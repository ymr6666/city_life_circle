## 一、本次会话完成的工作

### 1.1 路网数据增强：桥隧四档分类 + 模式可达列 ✅

**背景问题**：原 `hefei_roads` 只有 osmnx 默认保留的少量 tag，`bridge=yes` 无法区分"可走的过河桥"与"不能上的立交高架"；行人/骑行/驾车共用一套散落的过滤 SQL，且不一致。

**已完成动作**：

1. **增量抓取缺失 OSM tag**（`scripts/utils/enrich_roads_tags.py`）
   - 通过 Overpass 按 way id 分批拉取：`layer / foot / bicycle / motor_vehicle / vehicle / access / sidewalk / cycleway / surface / smoothness / lit / segregated / oneway:bicycle / incline`
   - 缓存：`cache/roads_tags.json`（21,412 条 way，约 85% 覆盖；其余为已删除的旧 way，走回退分类）
   - 支持 osmnx 合并后的 `[a,b,c]` 多 way osmid 聚合（access 类取最严格、layer 取最大、bridge/tunnel 取任一 yes）

2. **hefei_roads 新增列**：
   - 原始 tag 列：`layer, foot, bicycle, motor_vehicle, vehicle, access, sidewalk, cycleway, surface, smoothness, lit, segregated, oneway_bicycle, incline`
   - 派生列：`bridge_class`（四档物理结构）、`walk_ok / cycle_ok / drive_ok`（布尔可达列）

3. **四档桥隧分类规则**（`bridge_class`）：
   | 档位 | 判定 | walk | cycle | drive |
   |------|------|------|-------|-------|
   | `elevated` 立交高架 | bridge + layer>0（或 primary/secondary 无 layer 回退） | ✗ | ✗ | ✓ |
   | `tunnel` 车行隧道 | tunnel=yes + 车行等级 | ✗ | ✗ | ✓ |
   | `footbridge` 步行天桥 | bridge + footway/pedestrian | ✓ | ✗ | ✗ |
   | `bridge` 普通过河桥 | bridge + 低等级道路 | ✓ | ✓ | ✓ |
   | `none` | 非桥隧 | — | — | — |

4. **分类实测统计**（总边 104,130，cost>0）：
   ```
   walk  98,055 (94%)    cycle 97,506 (94%)    drive 88,489 (85%)
   bridge_class: none 100,148 | elevated 3,066 | tunnel 517 | bridge 237 | footbridge 162
   ```
   已抽样验证：motorway/trunk 禁行、普通住宅路全可走、天桥 walk可走 cycle禁行、高架禁行、车行隧道禁行、步行隧道可走等，无误伤。

### 1.2 引擎重构 + 统一多模式架构 ✅

**覆盖全部使用方式**（本次按需求设计并实现）：
```
单独道路:  walk | cycle | drive
道路+公交: walk+metro | walk+bus | walk+metro+bus   (metro/bus 为别名)
```

- **`backend/engine/walk_layer.py`**：删除散落的 `WALK_HIGHWAY_FILTER`，改为按 `hefei_roads.{ok_column}` 过滤；抽出 `ok_column / directed / poi_mode` 类属性，便于复用。
- **`backend/engine/cycle_layer.py`**：骑行层 `CycleLayer`（15 km/h、`cycle_ok`、`directed=True` 尊重单行道、排除 steps 与步行天桥）。`_edge_sql` 改用 `self.ok_column`。
- **`backend/engine/drive_layer.py`（新增）**：驾车层 `DriveLayer`（30 km/h、`drive_ok`、单行道、`poi_mode='drive'`）。立交/隧道不排除（机动车需上桥），"只能从匝道上下"由拓扑保证。
- **`backend/engine/transit_layer.py`（新增）**：**通用耦合引擎 `TransitLayer`**——统一图（道路边 + 地铁/公交边 + 换乘边），成本统一为分钟，单次 Dijkstra。
  - 节点偏移：路网 1~42785 / 地铁站 100000+ / 公交站 200000+stop_no
  - 公交边：`hefei_bus_line_stops` 相邻站连线，时间=直线距离/20km/h（`BUS_SPEED_KMH`）
  - **数据就绪检查**：bus 相关表缺失时抛 `ValueError` 明确提示（先 `--load` 再 `snap_bus_stops`）
  - 方向：walk 接驳 `directed=false`；cycle/drive 接驳 `directed=true` 尊重单行道
- **`backend/engine/metro_layer.py`**：重构为 `TransitLayer` 子类（road=walk, transit=('metro',)），输出字段向后兼容。
- **`backend/engine/bus_layer.py`（新增）**：`BusLayer`（walk+bus）、`WalkMetroBusLayer`（walk+metro+bus）。
- **`backend/engine/factory.py`（新增）**：`build_layer(mode)` 解析复合模式（`walk+metro+bus`、别名 `metro`/`bus`、非法输入报错）。
- **`backend/routes/isochrone.py`**：API 支持上述全部 mode；非法→400，公交数据未就绪→503。
- **`backend/test_walk.py`**：用 factory 构建层，通用输出（含公交站列表）。

**实测（市中心 31.861, 117.285）**：
| 模式 | 预算 | 可达路网节点 | 地铁/公交 | 可达 POI |
|------|------|-------------|----------|---------|
| walk 15min | 1,250m | 322 | — | 116 |
| cycle 15min | 3,750m | 1,516 | — | 362 |
| drive 15min | 7,500m | 5,551 | — | 2,165 |
| metro 30min | — | 8,704 | 126 站 | 2,530 |
| walk+metro 30min | — | 8,704 | 126 站 | 2,530 |
| bus / walk+bus / walk+metro+bus | — | — | — | 503（数据未就绪，待抓取） |

### 1.3 公交爬虫重写（适配真实配额） ✅

**真实约束**（个人认证实测）：公交接口 **日配额 100 次、限速 1 req/s**；合肥 4,000+ 站点、300+ 线路。

**`scripts/crawlers/crawl_bus.py` 重写要点**：
| 项 | 说明 |
|----|------|
| 限速 | `SLEEP = 1.1`（1 req/s 留余量） |
| 日配额 | `DAILY_QUOTA = 100`，默认 `run_daily()` 在预算内自动分配 Phase2/Phase3 |
| 配额保护 | `infocode 10003/10004` → 抛 `QuotaExhausted` 立即停止，**不烧配额重试**，先保存 checkpoint |
| 断点续跑 | 只有 `status=1` 成功才标记完成，失败项次日自动重查 |
| 饱和早停 | 连续 30 站无新线路 → 停止 Phase2（避免把 1,068 站全查完） |
| 坐标 | 落库前 GCJ-02 → WGS84（高德数据偏移合肥约 570m，路网为 WGS84） |

**爬取进度**：
| 阶段 | 状态 |
|------|------|
| Phase 1 网格搜站名（POI 接口，不耗公交配额） | ✅ 1,068 站名（99 请求） |
| Phase 2 stopname 发现线路 | ⚠️ 曾跑到 200 站收集 57 线路后撞配额；已 `--reset` 清标记，待重跑 |
| Phase 3 lineid 线路详情（有序站序） | ❌ 未开始 |
| 落库（hefei_bus_stops/lines/line_stops） | ⏳ 等数据齐，`--load` |

**逻辑已用不耗配额的模拟测试验证 4 场景**：配额中止保存 checkpoint、线路饱和早停、Phase3 中断保存、续跑补齐。
